# 多語貼文翻譯模組 — 規格

> 範圍:把「工作需求貼文」翻成多國語言並提供各語言分頁。
> **與身分驗證/工作權查核完全解耦**——這是獨立模組,可先做、先上、先試,不依賴 eKYC。

---

## 0. 這個模組做什麼 / 不做什麼

**做**:翻譯公開的需求貼文(刊登行為)、讓貼文者校對譯文、產生各語言可索引分頁、吃多語長尾 SEO。

**不做**:不判斷讀者/接案者的工作權(那是另一個模組的事)。翻譯一則公開資訊是合法刊登,與 §45 媒介無關。

**語言由貼文者自選(核心機制)**:語言**不是平台預設或依城市人口決定**,而是提供一個**中性語言菜單**,由貼文者逐則自選(英文為通用底層,再自行加第二/第三外語)。意圖與選擇權在貼文者,不在平台。因此語言清單同一份、跨城市通用,換城市不必改設定。

**平台被動中立(紅線)**:平台**不推薦、不引導**特定語言,**不做按族裔/語言篩掉應徵者**的功能。翻譯=讓更多人看懂(擴大、包容);嚴禁做成篩選(排除)。ToS 禁止歧視性招聘條件(族裔/原籍等受保護特徵)+ 檢舉入口 + 保留下架權。加拿大人權法管就業歧視,這道護欄讓責任留在貼文者、保護平台中立性。

---

## 1. 資料表設計

在既有 `job_requests` 加一個欄位:
- `source_lang`(原文語言,如 `zh-Hant`)

新增翻譯表:

**job_request_translations**
| 欄位 | 說明 |
|---|---|
| `id` | PK |
| `job_request_id` | FK → job_requests |
| `lang_code` | BCP-47,如 `vi` / `id` / `th` / `en` / `zh-Hant` |
| `title_translated` | 標題譯文 |
| `description_translated` | 內文譯文 |
| `source` | `machine` / `machine_edited` / `human` |
| `status` | `draft` / `published` |
| `translated_at` | 機器翻譯時間 |
| `approved_by` | 校對/核准者 user id(nullable) |
| `approved_at` | 核准時間(nullable) |

- 約束:`UNIQUE(job_request_id, lang_code)`
- 原文永遠存在 `job_requests`,譯文只存在這張表;兩者分離,方便重譯與稽核。

> 同樣模式未來可複製到技工簡介(`contractor_translations`),但本模組先只做需求貼文。

---

## 2. 翻譯觸發時機與流程

1. 貼文者送出需求(原文)→ 貼文先以原文發布,不被翻譯卡住。
2. **非同步**觸發翻譯 job(佇列),對「設定的目標語言清單」逐一呼叫翻譯 API。
3. 寫入 `job_request_translations`:`source='machine'`、`status='published'`,前端以**「自動翻譯」標籤**呈現(讓它立刻有用)。
4. 貼文者可在自己的貼文頁看到各語言譯文,並可**編輯**:
   - 編輯後 → `source='machine_edited'`(或 `human`)。
5. 重譯/新增語言:重跑該筆即可,不動原文。

> 為什麼非同步:翻譯 API 有延遲,不該擋住發文;也方便失敗重試與批次控管成本。

---

## 3. 貼文者校對

- 貼文者頁面列出「原文 + 各語言譯文」,每則可就地編輯、儲存。
- 譯文旁標示來源(自動翻譯 / 已由刊登者校對)。
- 這一步同時是**責任分配**:譯文正確性由刊登者確認,平台標示「翻譯供參考」。

---

## 4. 各語言分頁與 SEO

- 路由:每則貼文有各語言可索引 URL,如
  `/requests/{slug}`(原文)、`/vi/requests/{slug}`、`/id/requests/{slug}`。
- **只在該筆有對應譯文時才產生語言路由**——不自動產生空白頁(避免被 Google 判 doorway/thin content 反傷 SEO)。
- **hreflang**:每個語言版本互指,並含 `x-default`。
- 結構化資料(JobPosting / 一般 Posting schema)依語言輸出。
- 語言切換器:貼文頁提供 inline 切換,不靠重新搜尋。

---

## 5. 翻譯 API 與品質

- API:DeepL 或 Google Translate(先擇一,抽象成一層 adapter 方便日後替換)。
- **技工術語詞彙表(glossary)**:water heater / 熱水器、eavestrough、drywall、HVAC、furnace 等常錯詞先建表,餵給支援 glossary 的 API 或做後處理替換。
- **固定文案人工校對**:UI 字串、職類名稱、以及**任何法律免責文字**,不可純機器翻譯(免責被翻錯是真實風險),一次性請人校過。
- 成本:MVP 規模每月約 CAD/TWD 等值數十元;非同步 + 只翻已發布貼文可控管用量。

---

## 6. 邊界與注意

- 聯絡資訊維持既有的「點擊揭露」規則,**不因語言不同而改變**遮蔽邏輯。
- 語言為**貼文者自選的中性菜單**(如 en / zh-Hans / zh-Hant / tl / vi / id / hi / pa…),整份菜單登記在系統、跨城市通用;貼文者逐則點亮,平台不預選、不推薦。原文語言記在 `source_lang`。
- 譯文不改變貼文的審核/檢舉/下架流程;下架原文時,對應譯文一併隱藏。

---

## 7. Definition of Done

- [ ] 發文以原文即時發布,翻譯非同步產生、失敗可重試
- [ ] `job_request_translations` 建表,原文/譯文分離,`UNIQUE(job_request_id, lang_code)`
- [ ] 自動翻譯以「自動翻譯」標籤呈現,貼文者可編輯/校對
- [ ] 各語言分頁**僅在有譯文時產生**,無空白/薄內容頁
- [ ] 每語言版本 hreflang(含 x-default)互指正確
- [ ] 職類/UI/免責文字經人工校對;技工術語詞彙表已套用
- [ ] 語言清單可設定,依市場證據挑選
- [ ] 原文下架時譯文一併隱藏

---

### 一句話
翻譯是獨立、合法、低成本的模組,現在就能做;守住「只在有內容時產生語言頁 + hreflang + 免責人工校對」三點,它就是乾淨的 SEO 長尾放大器,而不是負擔。
